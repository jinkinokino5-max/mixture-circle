# STUDIO PULSE IV — 音楽を「生成」する版（studio-app-v7）

v5 までは **書いておいたパターンを再生する**アプリだった。
v6 は **その場で音符を作る**アプリになった。
v6.1 は音割れとメモリ膨張という「土台」の不具合を直した。
v7 は「芸術的な音楽をシンプルな操作で」というビジョンのもと、
サイクル3（案H〜）で音の中身そのものの表情を足していく版。

カードは v5 と同じ **40楽器 × 3つの弾き方 ＝ 120枚**。
ただし **40個のキーを覚える必要はもうない** ── engine が「つぎに足すと良い3枚」を
出すので、<kbd>←</kbd><kbd>↓</kbd><kbd>→</kbd> の3つだけで遊べる。

---

## 1. 使い方

1. **`音源をダウンロード.bat`** を最初に1度だけ実行（インターネット接続が必要／約43MB）
2. **`はじめる.bat`** をダブルクリック → ブラウザが開く（ポート **8772**）
3. 「はじめる」を押す。あとは <kbd>←</kbd><kbd>↓</kbd><kbd>→</kbd> で提案を採用していけば曲になる

v4（8769）／v5（8770）／v6（8771）とポートが違うので、同時に立ち上げて聴き比べられる。

## 1.5 v6.1 の修正（土台の不具合）

v6 を実際に聴く前提で洗い直したところ、構造的な不具合が2つ見つかった。

- **音割れ**：`Tone.Limiter` は内部がゆるい圧縮器でブリックウォールではなく、
  打楽器の立ち上がりが 0dBFS を超えて出力段でデジタルクリップしていた。
  → ハードニー圧縮＋最終段のソフトクリッパ（tanh）に置き換え、
  reverb/delay も `partsBus` 経由にして枚数ぶんの絞りを効かせた。
  出口レベルを見張るガードも追加し、詰まったら静かにマスターを下げる。
- **プツプツ切れる（音の欠落）**：mp3 はディスク上 42MB でも、Web Audio は
  再生のために Float32 の生波形へ展開して丸ごと抱える。実測 **437MB**。
  これがメモリを圧迫してGCが頻発し、音声スレッドが締め切りに間に合わなく
  なっていた。→ デコード直後に頭から3.5秒だけ残し、モノラルにまとめて
  **151MB（66%減）**。304本の同時デコードも6レーンに分けてロード時の
  フリーズを解消した。

いずれも「聴いてみないと分からない」種類の不具合で、実際に確認したことで
初めて直せた。詳しくは `tools/check-leak.js` / `tools/check-memory.mjs`。

## 2. v5 から変わったこと（サイクル1の5案 ＋ サイクル2の5案 ＋ サイクル3・案H/G/I/J ＋ サイクル4・案K）

### 案1 ── パートが互いを聴く

v5 では120枚すべてが「耳の聞こえない演奏者」で、同じ16分の位置に平気で音を置いていた。

v6 は小節の頭で **「16ステップ × 帯域（低・中・高）」の占有表** を作る。

1. まずドラム（骨格）が自分の位置を書き込む
2. 続いて音階のあるパートを **投入順** に生成する
3. 先に入ったパートほど好きな場所を取れて、後から入ったパートは埋まっていない場所へ逃げる

結果、**自動的に掛け合いになる**。ハイハットも、上ものが埋めている位置では自動で間引かれる。

実測：埋まっている位置に音を置く割合は **32%**（避けなければ50%以上になる）。
中域に2枚重ねたときの位置かぶりは **29%**。

### 案2 ── パターンを「配列」から「制約＋生成」へ

v5 は `pat: [{s:0,d:2,v:.85,l:'8n'}, …]` を120枚ぶん手書きしていた。
v6 の各カードは **どう弾くか（shape）を宣言するだけ**。

```js
{ tag:'刻み・転がる16分',
  shape: { d:13, syn:.35, cont:'wave', rng:[0,6], len:'16n', vel:.55 } }
```

| 項目 | 意味 |
|---|---|
| `d` | 1小節あたりの音数（＝密度）。変化1/2/3 の正体 |
| `pref` | 好むステップ |
| `syn` | シンコペーション 0..1。上げると裏拍へ寄る |
| `cont` | 音の輪郭 `up` / `down` / `arch` / `valley` / `wave` / `static` |
| `rng` | 構成音インデックスの範囲 |
| `poly` | 同時発音数（和音） |
| `walk` | ベース専用。`root` / `move` / `walk` / `oct` |
| `glue` | 高いほど「前の小節と似た形」になる（パッド向け） |

乱数は **カードIDと小節番号から決定的に**作る。
同じ場所は何度再生しても必ず同じ音になる（＝録音と演奏が一致する）が、
小節が進めば毎回ちがう音符が出る。**同じ4小節の繰り返しではなくなった。**

### 案3 ── 曲の時間構造（アレンジ・エンジン）

v5 は4小節ループが延々続くだけで、4分回しても「曲」にならなかった。
v6 は経過時間で章を進める。

```
導入 → 展開 → 持ち上げ → 山 → 間 → 締め → 終息
```

章ごとに **密度・ENERGY・ハイパス・残響の深さ** が変わり、変わり目にクラッシュが1発入る。
手で ENERGY を触ったら **30秒だけ自動が引っ込む**（人の操作を上書きしない）。

### 案4 ── グルーヴを一級の模型に

v5 は `time + ±3ms の独立乱数` だけだった。人間の揺れは前の音を引きずるので、
独立乱数はかえって機械的に聞こえる。

v6 は楽器ごとに **push（前ノリ／後ノリ）・tight（ばらつき）・drag（引きずり）・accent（拍ごとの強さ）** を持つ。

| プロファイル | push | 効果 |
|---|---|---|
| `bass` | −7ms | 足元が前へ。走って聞こえる |
| `kit` | −2ms | 土台は正確に |
| `hat` | +9ms | 金物は後ろへ。抜けが出る |
| `wind` | +12ms | 管は息のぶん遅れる |
| `bow` | +15ms | 弓は立ち上がりが遅い |
| `machine` | 0ms | 機械は揺れない（tight 0.8ms） |

ばらつきは **1次自己回帰**（前のずれを `drag` の割合だけ引きずる）。

### 案B ── engine が「つぎに足すなら」を3つ出す

**このアプリでいちばんビジョンと矛盾していたのが操作の複雑さ**だった。
40キー × 3変化＝120枚は、覚えることが多すぎる。

v6 は engine 側が候補を3つだけ出す。<kbd>←</kbd><kbd>↓</kbd><kbd>→</kbd> のどれかを押すだけ。

点数の付け方：

- 空いている ROLE を強く推す（土台が無いのに飾りを足しても始まらない。rhythm → bass → chord → melody の順に重い）
- **始めたばかりのときは必ず「基本」から**（何も無いところへ「刻み」を入れても曲は始まらない）
- 賑やかなら「余白」、寂しいなら「刻み」を推す
- 章に合う密度を推す（導入は薄く、山は厚く）
- すでに鳴っている音源と音色がかぶるものは下げる
- **キック持ちは3つの中に1つまで**（土台は1枚なので、2つ並べても片方は死ぬ）
- 3つとも同じ役割にはしない

下のカード表（120枚）はそのまま残してある。**自分で選びたい人のためのもの**で、
提案だけで遊んでもいいし、混ぜてもいい。

### 案C ── 強さで音色が変わる

v6 まで、強く弾いても弱く弾いても **音量が変わるだけ**だった。
実際の楽器は、弱く吹いたサックスは丸く、強く吹くと開く。

lp を「いちばん開いたときの明るさ」と読み替え、弱い音ほど閉じる。

```
cut = lp × ( open + (1 − open) × v ^ curve )
```

v=1 でちょうど lp になるので、**設定した明るさより明るくはならない**
（＝実測で合わせた音量バランスを壊しにくい向きに倒してある）。
楽器の系統ごとに効き方が違う（管は `open .32`、パッドは `.68`）。

実測：サックスで **弱 4921Hz / 強 8146Hz**（設定 8500Hz）。

### 案D ── 左右と奥行きに置く

v6 まで、全パートが同じ1点で鳴っていた。`pan`（左右）と `depth`（奥行き）を持たせた。

- **低音（ベース）と土台は必ず中央。** 左右に振ると芯がぶれる
- **同じ ROLE の2枚目は左右反転**して置く（重ねたとき混ざらない）
- 面で支える音は奥へ（パッド 0.78 / ストリングス 0.72 / ホルン 0.66）
- 奥ほど残響が増え、高域が落ちる（＝空気による減衰。これが「遠さ」の正体）

信号の道すじ：`voice → hp → lp(音色) → gain → air(距離) → panner → roleBus`

### 案A ── 章ごとに転調する

4分間ずっと Cマイナー1つだと、どれだけ音符を工夫しても「習作」の響きが残る。

ただしこの作品の生命線は「何と何を重ねても必ず噛み合う」こと。
自由な転調はそれを壊すので、**共通音による転調だけ**を許す。

移調先の条件は2つ：

1. **いまの調と共通音が2つ以上**（行きが滑らか）
2. **原調とも共通音が2つ以上**（帰りも滑らか）

②が要る理由：曲の終わりでは必ず原調へ帰す。行きだけを見て遠くまで行くと、
帰り道が飛び石になってそこだけ唐突に聞こえる。
**最初この②が無くて、検査が「-2→0 は共通音1個」と拾った。**

原調から動ける先（進行ごとに違う）：`night 沈晴飛 / sunrise 沈翳飛 / spell 沈晴飛 / city 沈晴飛`

転調はコードそのものを移調する形にしてあるので、下流（音名の解決・各パート・検証ツール）は
一切変更が要らない。

### 案E ── 終わりを「止める」から「終わらせる」へ

`endGame` は3.2秒のフェードアウトだけだった。フェードアウトは録音を止めただけで、
曲が終わった感じがしない。4小節かけて：

1. コード進行をトニックへ寄せる（帰ってきた感じ）
2. リタルダンド（最後の2小節で25%遅く）
3. 最後の小節でリズムを抜く
4. クラッシュ＋キックの一撃 → 残響だけ残して消える

<kbd>Esc</kbd> で終止つき、<kbd>Shift</kbd>+<kbd>Esc</kbd> で即停止。

### 案H ── ロングトーンの脈動（サイクル3・v7で追加）

v6.1 までは、音は「鳴り始め」と「鳴り終わり」しかなかった。四分音符より
長く伸びる音は、伸びている間ずっと無表情のまま。人が長い音を伸ばすときは
必ず微かに揺れる ── その「歌っている」感触が無かった。

本物のビブラートはピッチが揺れるが、この構成（`Tone.PolySynth` を含む
複数の合成器種）に安全にピッチ自動化を掛けるのは壊れやすい。そこで
**音量と明るさ（lp）を同時にごく僅か脈動させる**ことで、同じ知覚的な
効果をねらった：

```
振幅（4点の折れ線でサインカーブを近似）
  gain  = g0 × (1 + amp    × sin)
  lp    = l0 × (1 + bright × sin)
```

- 四分音符以上に伸びる音だけが対象（短い音を揺らすとわざとらしい）
- 鳴ってからワンテンポ遅れて揺れ出す（`delay`。人が音を伸ばす間と同じ）
- 揺れの深さ・速さは案C／案Dと同じ「楽器の系統」ごとに決める
  （息もの・弓ものは深く、鍵盤・機械はほぼ揺れない）
- **新しいノードは作らない** ── すでにある `this.gain` と `this.lp` に
  時間差の値を後から置いていくだけ。120枚×16小節を回しても
  ノード数は増えない（`npm run check:leak` で確認済み）

チップ「長い音を歌わせる」でオン・オフできる。

### 案G ── 周期の多様化（サイクル3・v7で追加）

v6.1までは、どのカードも「1小節でひと回り」だった。パッドのように
`glue`（前の小節と似せる度合い）が高いカードは、種そのものは数小節
（2/4/8小節＝`period`）に1回しか変えないのに、その `period` 小節の
あいだは**まったく同じ表情が繰り返されるだけ**で、「せっかく長く
持たせているのに、フレーズとして動いていない」状態だった。

そこで `period` を「1つのフレーズ」とみなし、フレーズの中の進み具合
`phase`（0→1）を輪郭と密度に反映させた：

- **輪郭**：`arch` や `wave` のような形が、1小節の中だけでなく
  **`period` 小節がかりの弧**を描くようになる（`up` のパッドなら、
  4小節かけてゆっくり音域が上がっていく、など）
- **密度**：フレーズの後半ほど僅かに音数が増える（0.86倍→1.14倍）。
  「始まって、満ちていく」呼吸ができた

`period` が1のカード（`glue` が低い大半のカード）は `phase` が常に0の
ままなので、**この案の影響を一切受けない**。ドラムやリズムのように
1小節で完結してほしい楽器はそのまま、面で支える楽器だけがフレーズ化する。

`tools/check-music.js` に、輪郭が実際に向きどおりの弧を描いているか
（`up` なら最後の小節のほうが音が高いか等）を確かめる検査を追加した。

### 案I ── ブレイク（サイクル3・v7で追加）

演奏中に起きる「事件」は、これまで<kbd>スペース</kbd>のビルド→ドロップ
1種類しか無かった。**盛り上げて落とす**の逆、**抜いて溜める**を追加した。

<kbd>Shift</kbd>+<kbd>スペース</kbd> でブレイク（`B` はすでに RHYTHM の
楽器キーなので使えない。ビルドと対になる「逆スペース」にした）：

1. 1小節、ドラム以外を静める（`partsBus` を12%まで絞る）
2. 4拍目の裏だけ、スネア1発を残す（止まっていることを分からせる目印）
3. クラッシュを使わず、キック1発だけで静かに再開する
   （ビルドの戻り方＝クラッシュ＋トムと対にして、単調にならないようにした）

`triggerBuild` と同じ `partsBus` 操作の型を流用しているので、
新しい信号の道すじは増えていない。ビルド中／既にブレイク中は無視される
（多重発火の防止）。`tools/check-engine.js` に、仕込みの数と
`State.breaking` の立ち下がり・多重発火防止を確かめる検査を追加した。

### 案J ── ROLEごとの4トラック書き出し（サイクル3・v7で追加）

これまで録音は1本の webm だけで、聴き返す以外の使い道が無かった。
**MELODY／CHORD／BASS／RHYTHM をそれぞれ別トラックとしても保存**できる
ようにした。DAWに読み込めば、ここで生成した演奏を土台に続きを作れる。

- 仕組み：各 ROLE バス（`duck`/`dry`）の出力を、聞こえ方に使っている
  配線はそのままに、専用の `Gain` へもう一系統だけ分岐させ、
  そこに ROLE ごとの `Tone.Recorder` を挿す
- 演奏の開始・終了と同時に、全体の録音と4トラックが同時に回る
- 曲が終わると「できあがりました」画面に、実際に録れたトラックの
  ぶんだけダウンロードボタンが並ぶ

**制約（正直に書いておく）**：reverb / delay はパートごとに共有バスへ
直結しているため、この4トラックには乗らない。つまり全体ミックスより
幾分ドライに聞こえる。完全な意味でのステム分離ではなく、
「役割ごとに聴き分けられる」程度の割り切りだと理解してほしい。

### （保留）案F ── 拍子の多様化

サイクル3の当初計画では「3/4・6/8 も鳴らせるようにする」案Fを予定していた。
着手前に見積もり直したところ、いまの生成エンジンは
**16ステップ固定**（`Tone.Transport.timeSignature = 4`、占有表もSequenceも
16分音符ベース）が土台の隅々まで前提になっており、カードごとに拍子を
変える／混在させるには、占有表・グルーヴ・フィル生成・アレンジ章立てが
軒並み書き直しになる。いま急いで通すと壊れたまま気づきにくい形で残る
リスクが高いと判断し、**設計をやり直したうえで単独のサイクルとして
着手する**ことにした（先送りであって、取り下げではない）。

### 案K ── 終止のバリエーション（サイクル4で追加）

案E（終止）はどんな曲でも「クラッシュ＋キックで締める」の1種類だった。
ENERGY を「静」のまま演奏していた曲まで同じ一撃で締めると、
静かに紡いできた曲がそこだけ唐突に映る。

そこで、終止に入った瞬間の ENERGY によって終わり方そのものを変えた：

- **熱／走**（ENERGY 2〜3）：従来どおり。クラッシュ＋キックの一撃で締め、
  画面もフラッシュする
- **静**（ENERGY 1）：一撃を使わず、キック1発だけで静かに溶ける。
  フラッシュも出さない（静かな曲の余韻を壊さないため）

トニックへ帰る・リタルダンド・リズムを抜く、という前段3つの仕込みは
共通のまま、最後の一撃だけを分岐させたので、変更は小さく収まっている。
`tools/check-engine.js` に、ENERGY ごとに正しい終わり方が選ばれるかの
検査を追加した。

### 案5 ── 組み合わせの音量を実時間で釣り合わせる

120枚を1枚ずつ測って揃えても、実際に鳴るのは組み合わせで、その数は事前に測り切れない。

v6 は ROLE ごとのバスを挟み、master を **4帯域**（低／中低／中高／高）で監視して、
帯域どうしの釣り合いを ROLE バスへ静かに戻す。

- **絶対値ではなく帯域間の相対バランス**を見る（絶対値だとパート数で全体が上下するたび4本とも振り切れる）
- 補正は **±4dB** まで、時定数 **2.5秒**
- 画面右下に、いまどれだけ補正しているかが出る

## 3. 操作

| 操作 | 内容 |
|---|---|
| `1`〜`0` | MELODY（曲の顔）10楽器 |
| `Q W E R T Y U I O P` | CHORD（曲の空間）10楽器 |
| `A S D F G H J K L ;` | BASS（曲の足元）10楽器 |
| `Z X C V B N M , . /` | RHYTHM（曲の動き）10楽器 |
| **同じキーをもう一度** | **変化 1 → 2 → 3 → 止まる** |
| **`←` `↓` `→`** | **提案された3枚を採用（これだけで遊べる）** |
| **スペース** | ビルドアップ＆ドロップ |
| **`Shift`+スペース** | ブレイク（1小節抜いて溜める） |
| `↑` / `Shift`+`↓` | ENERGY（静／走／熱）※触ると自動アレンジが30秒引っ込む |
| `Tab` | コード進行（夜／陽／呪／都） |
| `Backspace` | 最後の1枚を戻す |
| `Esc` | 終了（録音を書き出す） |

3つの変化：**1 基本** ／ **2 余白**（音数が少なく長い・下に敷く）／ **3 刻み**（音数が多く短い・上に乗せる）。
1小節あたりの平均音数は **基本 8.6 / 余白 2.9 / 刻み 16.7**。

画面の「自動でやること」で、**重なりを避ける／曲の流れを作る／音量を釣り合わせる／
強さで音色を変える／左右と奥行きに置く／終わりを締める／章ごとに転調する** を個別に切れる。
**演奏中に切り替えられる**ので、そのまま A/B 比較ができる。

## 5. 音量の決め方（実測）

耳ではなく、**実際に音を書き出して測って**決めている。
`node-web-audio-api` で本物の mp3 をデコードし、120枚それぞれを8小節ぶん
`OfflineAudioContext` で合成して、**ゲート付き LUFS**（ITU-R BS.1770）で測る。

音量は5段構え。

| 段 | 何を吸収するか | 決め方 |
|---|---|---|
| ① 音源の録音レベル差 | ピアノは大きく録れ、フルートは小さい | `samples.js` が読み込み時に実測（自動・±14dB） |
| ② 音数によるラウドネス差 | 1小節に1音と15音では聞こえ方が違う | `generateBar` が密度から自動補正（v6 で追加） |
| ③ 楽器の存在感 | この楽器をどのくらい前に出したいか | `sound.gain`。`tools/apply-gain.mjs` が実測から書く |
| ④ 変化ごとの差 | 変化1/2/3 の残差 | `variant.trim`（±6dB）。`tools/apply-trim.mjs` が書く |
| ⑤ **好み** | 「旋律はもっと前へ」など、その日の好み | `app.js` の `ROLE_TRIM_DB` ／ 画面のつまみ（**手で決める唯一の段**） |

**①〜④は実測で自動的に決まる較正の段**で、`npm run balance` を回すたびに
書き直される。手で触ってはいけない。
**⑤だけが人のための段**で、較正の上に乗るので上書きされない。

### 音量を自分で調整したいとき（⑤の使い方）

1. 画面の **「音量（役割ごと）」のつまみ**を、鳴らしながら動かす（すぐ反映される）
2. 決まったら **「いまの値をコピー」** を押す
3. 出てきた1行を `app.js` の `ROLE_TRIM_DB` に貼る → 次からその音量で始まる

> **0 以外にした役割は、自動ミックスの対象から外れる。**
> 自分で決めた値が勝手に動かされないようにするため。触っていない役割では
> 自動ミックスはこれまでどおり働く。
> （そうしないと、たとえばリズムを -8dB にしても自動側が上限の +4dB まで
> 押し戻してしまう。帯域と ROLE の対応はおおまかで、高域はリズムだけでなく
> 上ものも含むため。実測して分かった。）

全体の方向そのものを変えたいときは、較正の基準
`tools/apply-gain.mjs` の `ROLE_TARGET` を動かして `npm run balance` を回す。

**②は v6 で新しく入れた段。** v5 では ①③④ だけで釣り合わせようとして、
±6dB の trim では足りない箇所が7枚残っていた。密度から自動補正するようにしたら1枚に減り、
最後の1枚は shape 側を直して解消した。

### ROLE どうしの釣り合い（v7.1 で作り直した）

v7 までの `apply-gain.mjs` は「その ROLE の中央値」に各楽器をそろえるだけで、
**ROLE どうしの釣り合いは誰も見ていなかった**。実測すると

```
変更前   BASS -24.4 / RHYTHM -26.8 / MELODY -29.2 / CHORD -37.2 LUFS
```

コードはリズムより 10dB 以上下＝重ねてもほぼ聞こえない状態だった。
これが「ドラムばかり鳴って他が聞こえない」の正体。

そこで基準を **絶対値**（`ROLE_TARGET`）にして、合奏したときの立ち位置を
数字で決め打ちにした。あわせて、`music.js` が `INSTRUMENTS` より前に
同じキーの定位テーブルを持つせいで **13楽器が黙って補正から外れていた**
バグも直した（`indexOf` が定位テーブルのほうを掴んでいた）。

```
変更後   MELODY -25.5 / BASS -27.6 / RHYTHM -28.1 / CHORD -29.9 LUFS

変化1/2/3 のあいだの音量差： 平均 0.21dB
ROLE の中央値から 5dB 以上ずれたカード： なし（変更前は9枚）
パート単体で 0dBFS を超えたカード： なし
     ※薄い層（木琴・シェイカー・ボンゴ・ライド）は
       重ねる前提なので意図的に基準より 3dB 低い
```

## 6. 検証ツール（`tools/`）

v5 まで一時ファイルに置いていた検証スクリプトを、本体に入れた。
音楽アプリの「正しさ」はコードを読んでも分からない。実際に走らせて測るしかない。

```bash
npm run check          # 音楽データ＋エンジンの全検査
npm run check:music    # 音名・音域・密度・決定性・章立て
npm run check:engine   # Tone.js 抜きで app.js を実走（120枚 × 16小節）
npm run measure        # 実際に音を書き出して LUFS を測る（要 npm install）
npm run balance        # 測る → gain 修正 → 測る → trim 修正 を一気に
```

| ファイル | 何を見るか |
|---|---|
| `tools/check-music.js` | 120枚 × 4進行 × 16小節を生成して音名を解決／要求音域と音源の突き合わせ／3つの変化の約束（余白＜基本＜刻み）／生成の決定性／衝突回避が効いているか／章立て |
| `tools/check-engine.js` | Tone.js と DOM をスタブして本物の app.js を実走。全カードの発音・キー巡回・占有表・章の進行・グルーヴ・自動ミックス |
| `tools/measure-loudness.mjs` | mp3 をデコードして実際に合成し、ゲート付き LUFS で測る |
| `tools/apply-gain.mjs` | 実測から **楽器どうし**の音量をそろえる（基準は `ROLE_TARGET`） |
| `tools/apply-trim.mjs` | 実測から **変化1/2/3** の音量をそろえる |
| `tools/apply-centroid.mjs` | 実測した**明るさ**（スペクトル重心）を `sound.centroid` に書く |
| `tools/check-spacing.mjs` | 同時に鳴る音が**同じ臨界帯域(ERB)に入っていないか**を全数で数える |

### フレンチホルンの差し替えを見送った理由（実測による判断）

`reference/音源と楽器リサーチ.md` は「フレンチホルンは C4→D5 が14半音あき、
**±7半音＝音響スケール50%変化**。測定した中で唯一明確に壊れている」として
音源の差し替えを優先度1に挙げている。音源の性質としてはそのとおりだが、
**アプリが実際に使う範囲では、その移調は一度も起きていない**。

```
【実測】french-horn の移調幅（全カード × 全進行 × 8小節）
  ±0 半音   177回  24.0%
  ±1 半音   364回  49.5%
  ±2 半音    88回  12.0%
  ±3 半音   107回  14.5%
  ±7 半音     0回   0.0%   ← 資料が警告した値は発生しない
```

`chord-horn` の `rng` を 3 に制限してあるため、そもそも C4→D5 の穴を跨がない。
85.5% は JND 以下の ±2 半音以内に収まっている。

残る本当のコストは2つで、どちらも差し替えを急ぐほどではないと判断した。
- 14.5% が ±3 半音（19%変化。ホルンの JND 約7%は超える）
- C4〜D5 の音域が使えない（＝1オクターブ以上を捨てている）

なお配布元（tonejs-instruments）に不足音が無いことは HEAD リクエストで
全音名を確認済み。差し替えるなら VSCO2 CE（CC0）か Iowa MIS（無制限）から
取ってくることになり、外部音源の同梱・ライセンス表記・形式変換
（この環境には ffmpeg が無く mp3 化できない）が付いてくる。

この検査は実際に不具合を見つけている。v6 の開発中だけでも
「ハープの9半音移調」「パッド系4楽器の密度逆転」「自動ミックスの振り切れ」を検出した。

`npm run measure` だけ `node-web-audio-api` が必要（`npm install` で入る）。
`npm run check` は依存なしで動く。

## 7. ファイル構成

| ファイル | 役割 |
|---|---|
| `music.js` | 音楽の理屈／グルーヴ／40楽器×3 shape／**生成エンジン**／章立て。音は鳴らさない |
| `app.js` | 音響エンジンと画面。小節ごとの再生成・占有表・アレンジ・自動ミックス |

| `server.js` | 簡易サーバ（ポート 8771） |
| `tools/` | 検証・測定スクリプト |

**`music.js` は音を一切鳴らさない純粋な計算**なので、`tools/` からそのまま読める。
これが「ブラウザを開かずに音楽の正しさを検査できる」理由。

## 8. RFIDリーダーが届いたら

1. メモ帳を開いてタグをかざし、打ち込まれる UID を控える

3. そのまま `はじめる.bat` で開けば、かざした瞬間に音が入る

物理カードは **1枚 = 1つのID**。「ギター」は3枚のカードになる。

## 10. 確認済み／未確認

**確認済み**（すべて `npm run check` で自動）

- 120枚 × 4進行 × 16小節を生成して音名解決に破綻なし
- 生成が決定的（同じカード・同じ小節なら必ず同じ音＝録音と一致する）
- 3つの変化の約束（余白＜基本＜刻み）
- 要求音域と音源の音域の突き合わせ（6半音超の移調は解消済み）
- 120枚すべてが16小節で発音・例外なし・グルーヴで時刻がずれている（120/120）
- 案1 占有表が埋まり、中域2枚のかぶりが29%
- 案3 7つの章が順に進み、手動 ENERGY が自動に上書きされない
- 案5 自動ミックスが動き、±4dB を超えない
- 音量（第5節）。パート単体で 0dBFS を超えるカードなし

**未確認 ── 実際に耳で聴いた印象**

1. **生成パターンが音楽的に良いか。** これが v6 最大の未知数。
   v5 の手書きパターンは「音楽的に良いと分かっているもの」だったのに対し、
   v6 は制約から作るので、**平均点は上がっても当たり外れが出る可能性**がある。
   聴いて shape の値（特に `syn` と `cont`）を詰める余地が大きい。
2. **合成シンバルの音量。** ライドは測定上まだ基準より約 15dB 低い。
   ただし `Tone.MetalSynth` を Node で再現できず帯域ノイズで近似しているため、
   実際より小さく出ている可能性が高い（v5 から続く既知の限界）。
3. **グルーヴの効き具合。** push の値（−7〜+15ms）は音楽的な常識から置いたもので、
   測定では「ずれていること」しか確認できていない。
4. フレンチホルンは音源の C4 と D5 の間が14半音あいている。低い側だけ使っている。
