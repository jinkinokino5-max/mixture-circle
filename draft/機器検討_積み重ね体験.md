# 「積み重ねる」体験を実現する機器の再検討

作成日：2026-08-07
対象：`draft/実装計画.md` 1章（システム構成）・5章（箱の設計）の再検討
背景：ゲームの本質は「円になり、カードという物質を積み重ねて音楽をつくる」こと。
現行案がこの本質を技術面でどこまで体現できているかを見直す。

---

## 0. 結論（先に3行）

1. 現行計画（USB HID RFIDリーダー＋NFCシール）は、**「投入→通過→トレイに落ちる」**という一方通行の動きで、積み上がるのはあくまで結果。"積み重ねる"手応えそのものは弱い。
2. 「積み重ねる」を技術の根っこから体現するなら、**カードの縁に印刷パターンを持たせ、反射型光センサ数個で読み取る「光学バーコード方式」**が最有力。RFIDシール代（1,500〜3,000円）が丸ごと不要になり、かつ光センサ＋マイコンでの読み取りは今後の工作全般に応用が利く基礎技術。
3. ただし「今どの音が鳴っているかが物理的な配置で一目でわかる」体験（＝一番"積み重ね"の本質に近い）を求めるなら、**枠ごとにセンサを仕込む「陣地（ポケット）方式」**が最も体験に忠実。配線量が増える分、Phase 1でいきなりは難易度が上がる。

**先に判断していただきたいこと：** 3方式のうちどれを軸に検討を進めるか（このあとAskUserQuestionで伺います）。

---

## 1. 現行計画の弱点（再確認）

`実装計画.md` の箱設計：

```
投入口 → 傾斜スロープ（滑走） → RFIDリーダーで検知 → カード受けトレイに落ちる
```

- 検知は「通過した瞬間」の一点のみ。カードはその後トレイに落ちて役目を終える。
- 山になるのは事実だが、**山の形・置き場所に意味がない**（ただの排出先）。
- 「誰が・どの音を・いつ足したか」を後から目で追いにくい（トレイの中でカードが混ざる）。
- 一方で：**実装がほぼ固まっており、追加費用も最少**。Phase 1をとにかく早く形にしたいなら合理的。

## 3. なぜ「カードを直接重ねてRFIDで一括読み取り」は採らないか

一見、企画の「積み重ね」に一番忠実なのは「NFCシールを貼ったカードをそのまま物理的に積み重ね、下のリーダーで重なった全部を一括検知する」ことに見えるが、これは技術的に採用しない。

- 13.56MHz帯のNFC/RFIDタグは、**すぐ近くで重なるとアンテナ同士が磁気的に干渉し合い（デチューニング）、一番上以外がうまく読めなくなる**という既知の弱点がある。
- 安価なHIDリーダーは基本的に「範囲内で一番強く反応したタグ」しか拾わない設計が多く、複数タグの同時識別（アンチコリジョン）に対応していても、**直接重ねた状態での複数読み取りは信頼性が低い**。
- 対策として「タグ同士を数cm離す」必要があり、結局「直接積み重ねる」という体験と矛盾する。

→ この理由から、B案・C案のように**RFID以外の識別方式**、またはA案のように**識別と「積み上がる場所」を分離する**設計のどちらかが現実的。

## 4. 各方式の詳細

### A. 現行維持＋見せ方調整

- 変更点：カード受けトレイを箱の外・円の中央に置き、透明な器（ガラスボウル等）にする。読み取り後のカードが全員から見える形で積み上がっていく。
- 部品は`実装計画.md`の通り（USB RFIDリーダー、NFCシール）。
- **追加費用ほぼゼロ**。今すぐ着手できる。

### B. 光学バーコード方式（推奨）

```
カードの縁（1辺）に、楽器×ジャンルを表す白黒の縞模様を印刷
      │
      ▼ スロープを滑らせて通過
┌──────────────┐
│ 反射型光センサ ×5〜6個を一列に配置  │ ← TCRT5000等（約150〜300円/個、要確認）
│ （通過時に縞模様のON/OFFパターンを読む）│
└──────┬───────┘
       ▼
   ESP32（約1,800円、秋月電子で確認済み）で
   パターン→楽器×ジャンルに変換
       ▼
   PC/ブラウザへ送信（USBシリアル）
```

- 5〜6個のセンサ＝2進数5〜6桁＝32〜64通りを表現可能（企画書の最大50通りに対応）。
- カードは**紙に印刷するだけ**で複製できる。追加・差し替えが実質無料。
- 配線はブレッドボード＋ジャンパ線で足りる（はんだ付け不要）。`実装計画.md`のPhase 2で想定していた「ESP32入門」を、Phase 1の時点で前倒しする形になる。
- 弱点：カードの送り速度・センサとの距離を一定に保つ調整（閾値調整）が必要。最初の動作確認にRFIDよりは試行錯誤が要る。

### C. 陣地（ポケット）方式

```
円形の台に、楽器×ジャンルぶんの小さな仕切り（ポケット）を配置
   例）6楽器×4ジャンル＝24ポケット
        ┌───┬───┬───┬───┐
        │Pf/Jz│Gt/Jz│Bs/Jz│Dr/Jz│ …
        └─┬─┴─┬─┴─┬─┴─┬─┘
          │磁石検知（リードスイッチ）│
          └── I/Oエキスパンダ(MCP23017,約210円/個)で束ねる ──┘
              ↓
          ESP32 → PC/ブラウザへ送信
```

- カード裏に小さな磁石を貼り、対応するポケットに置くとそのポケットのリードスイッチがON→音が加わる。**抜くと音が止まる**ので、「今鳴っている音の一覧」が物理的な配置そのものになる。これが3方式の中で最も"積み重ねてつくる"に近い体験。
- リードスイッチは1個200〜300円程度（マルツ調べ、要確認）。24個で約5,000〜7,000円は超えないが、部品点数と配線が一気に増える。
- **現実的な始め方：** 最初から24ポケットは作らず、6楽器×2ジャンル＝12ポケットなど小さく試作し、良ければ拡張する。

## 6. 【追加提案】

- D案として「プレイヤーの人数ぶん、円周上にRFIDリーダーを複数配置し、各自の手元エリアに置かれたカードを常時検知する」方式も考えられる（＝"囲む"を最も文字通り再現できる）。ただしHIDリーダーを3〜6台使うと部品代だけで1万〜2.7万円になり、「安く作る」という目標と衝突するため、今回の推奨からは外した。将来、資金に余裕が出た場合の拡張案として温存する。
- どの方式を選んでも、`実装計画.md`のPhase 0で確立した「音楽エンジン側（Tone.js・拍同期・濁りの制御）」はそのまま流用できる。差し替わるのは`cards.js`とハードウェア入力の受け取り部分のみ。
